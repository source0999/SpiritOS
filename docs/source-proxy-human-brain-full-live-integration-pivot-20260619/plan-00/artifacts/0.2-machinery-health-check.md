## Cartographer — HEALTHY but preview-bounded at the API boundary

- Router: `source_proxy/api/cartographer.py` (2156 lines, prefix `/v1/cartographer`, mounted). Package: `source_proxy/cartographer/` (80+ modules incl. levels 2–14, workflow runtime, worker runtime, autonomy runtime, approval-token runtime + consumption, soak promotion, final-proof stages 1–7).

- Decision-bearing posture (KEY): the API is overwhelmingly **preview/approval-preview only**. Every git-mutating endpoint declares fail-closed flags — e.g. `cartographer_commit_proposal_validate` returns `api_preview_only: True, staging_enabled: False, commit_enabled: False, push_enabled: False, git_mutation_authority_granted: False` (lines 639–648); push endpoint returns `push_enabled: False, force_push_enabled: False, api_mutation_available: False` (lines 685–693); level-3 commit execution is `block_cartographer_level_3_commit_execution`; level-4 push is `block_cartographer_level_4_push_execution`. The approval-token status preview is explicitly `no-go`/`validation_only`/`preview_only`/`no_go_default: True` (lines 1194–1209).
- Real writes that DO exist: `safe-write` (`execute_safe_write_request`, gated by workspace root + token + kill switch), `docs-autopilot/apply`, `level-2/apply`, `clutter-proposals/{id}/approve`, `starter-blueprints/{id}/approve`, `apply-approved` — each gated and fail-closed on missing approval/workspace.
- Failure outcome: real where writes exist; preview endpoints return blocked payloads rather than mutating.
- Causal id: approval_token_id, run_id, proposal_id present. No invocation_event_id/consumer_event_id/consumer_subsystem/trace_id.
- Restart/resume: approval-token runtime + kill switch + level-11 event ledger modules exist (`level_11_event_ledger.py`, `workflow_event_ledger.py`, `workflow_state.py`) — ledger-backed resume is implemented at the design level; not verified live here.

Verdict: Cartographer is the most mature decision-bearing machinery in the tree, but its public API surface is deliberately preview/approval-only for git mutation. It is NOT a live autonomous executor today; it is a supervised-proposal system. Any Plan 1 MVI that wants "real whole-brain" execution must either (a) reuse Cartographer's approval-token + ledger primitives and add the missing causal events, or (b) treat Cartographer as the consumer-of-record for receipts. Decision deferred to Phase 0.3/0.5.

## Cross-cutting health findings

1. **No tracked subsystem emits the Plan 0 causal-event pair.** This is the gating health gap. Every "decision-bearing" verdict above is conditional: the machinery is real and fail-closed, but it does not produce `invocation_event_id` + `consumer_event_id` + `trace_id`. So the Plan 0 GO criterion cannot be satisfied by any current path.
2. **Two parallel "decision" vocabularies exist** that must not be conflated:
   - Plan-gate verdicts (this packet): `GO/NEEDS_FIX/BLOCKED_HUMAN/BLOCKED_ENV` — PARTIAL_GO forbidden.
   - Runtime health status (`runtime_health.py`): `GO/PARTIAL_GO/NO_GO/BLOCKED/UNKNOWN` — PARTIAL_GO is a legitimate health state, NOT a plan verdict.
   These are different layers and must never be cross-wired to produce a fake plan GO.
3. **Advisory vs decision-bearing split is clean in source:** routing advice (`/v1/decisions/route`) is clearly separated from execution (`/v1/tasks/long-running/*` + approval gate + cartographer). No code path lets advisory output mutate state directly.
4. **Git mutation authority is deliberately absent from autonomous paths:** cartographer commit/push endpoints are hard-blocked (`block_*`); apply happens only via the human-approved long-running task path. This is consistent with the Plan 0 "no authority expansion without Britton" rule.
