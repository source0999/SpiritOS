# 0.5 Thin-but-Real MVI Contract and Feasibility

Status: `TRUTH_FROZEN_READ_ONLY`. Plan 0 planning task. No source edits authorized; this defines the contract a future Plan 1 would implement, it does not implement it.

## MVI definition (Thin but Real)

The Minimum Viable Integration is: ONE decision-bearing subsystem produces a real invocation→consumer trace through the canonical route, with the operator as approval boundary, and failure provably changes the route or verdict.

"Thin": one subsystem, one consumer, no new framework, no autonomous git mutation, no Obsidian/Mac write.
"Real": causal identifiers exist, the consumer genuinely observes a changed state field, and a failure mode changes the outcome.

## Candidate MVI (recommended for Plan 1 consideration)

**Long-running task apply with shell-as-consumer.**

- Invocation: operator-approved `POST /v1/tasks/long-running/{task_id}/execute-approved` → `execute_approved_long_running_task` → `central_gate_check`.
- Existing real identifiers reused: `task_id`, `approval_id`, `run_id`.
- New identifiers to add: `invocation_event_id` (emitted at execute), `trace_id` (links the trace), `consumer_event_id` + `consumer_subsystem="CodingCockpitShell"` (emitted when the shell observes the `applied_needs_verification` transition).
- Changed state field: task `status` (`executing` → `applied_needs_verification`).
- Failure mode that changes outcome: central gate `gate_closed`/`gate_blocked`/`increment_mismatch`/`approval_token_missing` → apply blocked → status does NOT advance → consumer observes the blocked terminal state. This is the GO criterion's "failure changes the final route or verdict."

## MVI contract (what Plan 1 must deliver and prove)

1. Add `trace_id`, `invocation_event_id` emission at the execute-approved invocation (and optionally at task create).
2. Add `consumer_event_id` + `consumer_subsystem` recording in exactly one consumer when it observes a changed task status field.
3. Persist both events such that one trace contains the invocation event, the consumer event, the shared `trace_id`, and the changed state field.
4. Live proof artifact containing: `task_id`, `trace_id`, `invocation_event_id`, `consumer_event_id`, `consumer_subsystem`, before/after status, focused-check results, and git status.
5. Demonstrate the failure mode (e.g. closed gate) yields a different terminal status than success, in the same trace structure.

## Non-goals for the MVI (explicit exclusions)
- Not autonomous commit/push.
- Not multi-subsystem fan-out (one subsystem only).
- Not Obsidian/Mac/Scout writes.
- Not a new parallel state engine (reuse long-running task store; if an event ledger is needed, reuse a Cartographer ledger primitive, do not add a competing one — per 0.3 no-duplicate-machinery).
- Not deriving plan verdicts from runtime-health probes (per 0.4 no-conflation).

## Feasibility verdict
FEASIBLE, conditional on the causal-event contract. The MVI is buildable entirely on existing, healthy, decision-bearing machinery without crossing any Plan 0 hard stop. It does NOT require authority expansion, framework adoption, route replacement, or forbidden writes. The single hard dependency is introducing the four missing causal identifiers and proving a real consumer event — which is precisely the scope Plan 1 is chartered to attempt. No fake GO: this artifact asserts feasibility, not completion.
