# SpiritOS Campaign 3 - Extended Coding Lanes Integration

Terminal verdict:

`CAMPAIGN_3_EXTENDED_CODING_LANES_INTEGRATED`

## Problem

Foundation Remediation R1 proved the production-valid core coding lifecycle:

- canonical production orchestrator
- Source Proxy-owned task/run/attempt state
- versioned runtime contracts
- canonical context broker
- target-plugin enforcement
- model routing and declared fallback
- authority-bound execution
- independent reviewer
- independent verifier
- independent anti-cheat
- independent evidence recorder
- immutable evidence
- accountable recovery
- Undo/reset and clean rerun

SpiritOS still references or partially implements broader coding lanes without proving that they are genuine participants in this lifecycle.

The missing extended coding scope includes Scout and current web/documentation research, SearXNG-backed search, Obsidian project and coding knowledge, Mac worker and Mac-specific coding frameworks, retained coding sub-agents, extended context-model participants, platform-specific verification, cross-lane conflict resolution, truthful degradation and fallback, complete extended-lane observability, and a genuine all-lane coding proving task.

The operator cannot yet trust that a claimed lane actually ran, produced a real output, had that output consumed, followed canonical authority, degraded truthfully, or contributed to the same final coding artifact.

## Goal

Integrate every retained extended coding lane into the production-valid R1 coding lifecycle.

From one canonical coding task, SpiritOS must determine lane applicability, invoke selected lanes through runtime-enforced versioned contracts, consume required outputs, expose real state and provenance, resolve conflicts visibly, authority-bind writable operations, recover or degrade truthfully, produce one immutable source-bound receipt, and complete a genuine all-lane authenticated coding task from a clean isolated baseline.

A lane does not count as integrated because it appears in a prompt, exists in a registry, has a route, returns a preview, emits a placeholder, reports `performed:true`, is simulated by a harness, produces an output that no real downstream consumer uses, or is manually listed in evidence.

## Architecture Invariants

Campaign 3 extends R1. It does not replace it.

There remains one canonical coding orchestrator, task/run/attempt owner, context broker, lane registry, target-plugin authority, Approval Authority, executor, reviewer boundary, verifier boundary, anti-cheat boundary, and evidence model.

Extended lanes must plug into those boundaries. They may not create parallel orchestration, task stores, context ownership, approval stores, mutation paths, review systems, verification systems, evidence writers, or target resolution.

Writable does not mean unrestricted.

Every mutation-capable extended lane must use server-owned planning, exact root/target binding, canonical approval where required, canonical execution, verification, immutable evidence, and rollback or compensating recovery.
